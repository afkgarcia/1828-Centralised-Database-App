01 Requesting access

FLAG{R3QU3ST_CR4FT1NG}

Vulnerabilities

The vulnerabilities related to this level are broken access control, where privilege levels are determined by a client-provided admin field rather than a secure server-side session; a lack of integrity protection, where the request body is merely Base64-encoded JSON, so without any encryption or cryptographic signature an attacker can decode and modify the payload without detection; and a weak anti-replay mechanism, where the server checks a time field to reject stale requests, but because this timestamp is also client-provided and unauthenticated, it cannot prevent a freshly crafted request.

Exploitation

I first did some reconnaissance: decoding the Base64 requests revealed the JSON structure, and comparing a failed request to a successful one showed exactly what was needed. Replaying the successful admin:1 payload failed with a "too old" error, so to overcome this I generated a new payload with the current timestamp. Finally I wrote a small bash script to generate the current time, build the malicious JSON with admin:1, Base64-encode it, and send it via POST.

02 Handy online service

FLAG{$H3LL_1NJECT10N}

Vulnerabilities

The vulnerability related to this level is unauthenticated OS command injection, where the application takes user input and passes it directly to a system shell with no validation, sanitization, or sandboxing. In effect the entire feature is an open remote shell. This is made worse by a lack of authentication on the endpoint, so anyone who can reach it can run commands, and by excessive privileges, since the process runs as root, meaning a single injection gives full control of the host rather than a limited account.

Exploitation

I first did some reconnaissance, fetching the page source which revealed that the form posts JSON of the form {"command": ...} to the /shell endpoint with a JSON content type, and returns the output in the msg field. This meant I could call the endpoint directly with curl instead of using the web UI. I confirmed code execution by sending ls -la, which returned a real directory listing and showed a flag.txt file sitting in the application's working directory. Finally I sent cat flag.txt the same way, and the server returned the contents of the file.

03 Direct banking

FLAG{IDOR}

Vulnerabilities

The vulnerability related to this level is an Insecure Direct Object Reference (IDOR), where each account is served at /accounts/<username>.php with no authorization check. The server never verifies that the requester is actually the user whose account is being requested, so anyone can read any account simply by changing the filename in the URL. This is compounded by information leakage, since each account's transaction history displays the names of other account holders, which gives an attacker exactly the usernames needed to keep enumerating.

Exploitation

I first did some reconnaissance and noticed that the page was at /accounts/johndoe.php, which suggested accounts were keyed by the username in the filename, and that the naming convention was the first and last name in lowercase with no spaces. Listing the /accounts/ directory was forbidden and there was no admin account, so instead I used the data on the page itself: John Doe's transaction history named "Jane Doe" and "Jim Smith", so I requested janedoe.php and jimsmith.php, which both returned valid accounts. Jim Smith's transaction history in turn named a new account holder, "Bob Johnson", so I requested bobjohnson.php. Its transaction history contained an entry whose "From Account" column held the flag.

04 Verified hacker

FLAG{YOU_CANT_SEE_ME}

Vulnerabilities

The vulnerability related to this level is broken access control through client-controlled state, where whether a user is considered a "verified hacker" is decided by a hidden form field called state that is sent by the client. The form ships with state set to 0 (not verified), but because this value lives in the request and is fully controlled by the client, it can be tampered with. The server trusts it directly instead of tracking verification status server-side, and the check is effectively just "is state equal to 0?", so any other value is treated as verified.

Exploitation

I first did some reconnaissance and fetched the page source, which showed a form that posts to the /verified endpoint with two fields: the visible hackername text field and a hidden field state with value 0. Submitting the form normally (with state=0) returned "Sadly, you do not seem to be a verified hacker." I then resubmitted the same request but changed the hidden field to state=1. One detail worth noting for reproduction: the successful response body looked empty in the terminal at first, so I used curl -i (include headers) to view the full response, which revealed the flag. I confirmed afterwards that any value other than 0 produces the same verified result.

05 Guess!

FLAG{ROCK_PAPER_COOKIES!?}

Vulnerabilities

The vulnerability is client-side reliance on unsecured state through an unsigned cookie. A plaintext cookie called score stores the game's score with no encryption or signature, so the client can set any value. On each win the server increments the value read from the cookie, and awards the flag once it reaches the threshold, trusting attacker-controlled data. The game logic itself was valid; the flaw was storing the score in an editable cookie.

Exploitation

After reconnaissance, I pulled the page source and saw the form posts JSON {"guess":"0|1|2"} to the /game endpoint, and that the server tracks the score rather than sending it to the client. Inspecting the response headers with curl -si revealed Set-Cookie: score=0, confirming an editable cookie. I then sent requests with a forged score=999999 cookie. Since the server's move is random and I win roughly a third of rounds, I looped the same forged request until a winning round occurred. On that win the server added 1 to 999999, passed the threshold, and awarded the flag.

06 Guns N' Roses

FLAG{Sl4sh}

Vulnerabilities

The vulnerability is path traversal via an off-by-slash in an nginx alias directive, caused by a misconfigured block of the form location /flag { alias /.../flag/; }. The prefix has no trailing slash but the alias does. This mismatch lets an attacker escape the directory: when a URL matches the prefix, nginx strips /flag and appends the remainder to the alias path, so /flag../X resolves to /.../flag/../X, climbing above the served directory to read other files.

Exploitation

Visiting /flag.txt returned 404 even though / redirected to it. Any URL with extra path segments returned a 301 to /flag.txt, while URLs normalizing to /flag.txt returned 404, indicating a dedicated handler for the flag path and a catch-all for everything else. To find the handler's exact prefix I ran a case test: /flag.TXT returned 404, but /Flag.txt and /FLAG.TXT returned 301. The common factor of the 404s was the lowercase prefix /flag, revealing the real location prefix. Recognizing the off-by-slash, I requested /flag../flag.txt with curl --path-as-is so curl wouldn't collapse the ... nginx resolved this to the alias path plus ../flag.txt, returning the flag.

07 Worth a thousand words

FLAG{F0R3NS1CR3S3ARCH3R}

Vulnerabilities

The flaw wasn't in the web application but in how the flag was hidden inside one of the images. A JPEG ends at its FFD9 end-of-image marker, and bytes after it are ignored by viewers and browsers, so the picture displays normally while carrying a hidden payload. Here a gzip-compressed file called flag.txt was appended after the marker. The weakness is trailing content after a file's logical end: invisible when viewed, easily extracted from the raw bytes, and able to bypass header-only checks.

Exploitation

My reconnaissance found no web attack surface: the vote buttons had no backend, /static/ used the framework's safe handler so it couldn't be traversed, and there were no hidden endpoints. I then examined the images. Running strings revealed the filename flag.txt but no plaintext FLAG, so the contents were compressed. unzip failed, since there was no ZIP central directory. Inspecting the raw bytes around flag.txt, I saw the JPEG FFD9 marker followed by the gzip magic bytes (1f 8b 08 08), the stored filename flag.txt, a deflate stream, and a footer giving a 25-byte uncompressed size. I recovered the flag by carving from the gzip magic to end of file and decompressing with gzip.

08 Call me maybe

FLAG{Numbers!}

Vulnerabilities

The vulnerability is information disclosure with reversible obfuscation, not a server flaw. The flag was hidden on the page disguised as phone numbers, and the decoding instructions were left in a Base64-encoded HTML comment in the source. The digit groups in each fake number are decimal ASCII character codes.

Exploitation

I viewed the page source and found a Base64 comment, which decoded to an instruction: remove every phone number containing both a Fibonacci number and a prime number, and keep the rest. I confirmed the groups were ASCII codes, since one row decoded to readable text ending in ! and }. I applied the rule to all rows, discarding any that held both a Fibonacci value and a prime value. Two rows survived. Decoding their numbers as ASCII, including the country-code number, and concatenating them in page order produced FLAG{Nu then mbers!}. I used a short script to fetch the page, parse the numbers, apply the filter, and decode the survivors.

09 Teenage Mutant Jinja Turtles

FLAG{S4F3_T3MPL4T3}

Vulnerabilities

The vulnerability is Server-Side Template Injection (SSTI) in the Jinja2 template engine. The application takes user input and renders it as a template rather than passing it as inert data, so any template expression in the input is evaluated on the server. In Jinja2 this escalates from simple expression evaluation to full remote code execution.

Exploitation

I did some reconnaissance and fetched the page, which contained a form that posts a userinput field to the /render endpoint. I confirmed the injection by submitting {{7*7}}, which the server rendered as 49, proving expressions are evaluated server-side. To turn this into code execution and read the file, I used the Jinja built-in global lipsum, whose __globals__ attribute exposes Python's os module. I submitted {{ lipsum.__globals__.os.popen('cat flag.txt').read() }}, which ran cat flag.txt on the server and returned its contents in the rendered page.

10 Shrouded in darkness

Flag{0bscur3}

Vulnerabilities

The vulnerability is security through obscurity, a form of broken access control. The flag is served at a predictable, guessable path that is simply not linked anywhere on the site and is protected by nothing more than the assumption that nobody will find it. Since an unknown URL is not an access control, the page can be reached by anyone who requests the right path.

Exploitation

The page itself contained no links, comments, or hints, and only taunted that the flag would never be found. Because there was nothing to follow, I performed file and directory enumeration, requesting a list of common paths and watching the HTTP status codes. Both /flag and /flag.txt returned status 200 instead of 404, revealing hidden pages. I then requested /flag.txt directly and the server returned the flag in its response body.
